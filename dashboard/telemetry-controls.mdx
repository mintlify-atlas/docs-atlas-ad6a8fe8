The GeoMine dashboard sidebar hosts a single persistent `st.form` that consolidates every input needed to characterize the current drilling situation: geological zone selection, spatial search geometry, live surface sensor readings, and the AI toggle. Grouping all controls inside a form means Streamlit only re-runs the backend analysis when the engineer explicitly clicks **Run Drilling Risk Analysis** — slider and input changes are buffered locally until that moment, preventing unnecessary API calls on every minor adjustment.

---

## Spatial & Geological Parameters

The top section of the sidebar form configures the geological and geographic scope of the offset well search.

### Target Formation Zone

A selectbox filtering offset wells by their formation logged at 2,780 m depth. Only wells whose `formation_at_2780` field matches the selected value are included in the corridor analysis.

```text
Options: ["All", "Kopili Shale", "Girujan Clay", "Barail Coal-Shale", "Lakadong-Therria"]
Default: "All" (index 0)
```

Selecting `All` disables formation filtering and returns every nearby well within the radius and depth corridor regardless of lithology. Selecting a specific formation zone narrows results to wells sharing the same geological context as the active rig, producing higher-fidelity analog matches.

### Radial Search Buffer (km)

A continuous slider controlling the geographic search perimeter around the active rig's GPS coordinates. The GIS engine computes Haversine distance from the active well to every offset well in the repository and includes only those within this radius.

```text
Min: 1.0 km   Max: 50.0 km   Step: 0.5 km
Session state key: radius_km_slider
Default (on first load): 5.0 km
```

The active radius value is persisted in `st.session_state["radius_km_slider"]` so it survives re-runs. The eRTMAC simulator overrides this to 45.0 km when activated to ensure wells are visible at all simulated depths.

### Historical Depth Corridor (±m)

A slider setting the depth window around the current bit depth. Offset wells whose `event_md` (incident measured depth) falls within `current_depth ± depth_window` are included as valid historical analogs.

```text
Min: 30 m   Max: 150 m   Step: 10 m   Default: 80.0 m
```

A tighter corridor (e.g. ±30 m) produces more precise depth-matched analogs. A wider window (e.g. ±150 m) captures more wells but introduces shallower or deeper incidents that may be less directly relevant to the current bit position.

## Live Surface Sensor Inputs

The **Live Surface Sensors** block accepts the five real-time telemetry values from the rig's surface instrumentation. These values are passed directly to the risk analysis payload and are stored in `st.session_state["telemetry"]` after each analysis run.

| Parameter | Widget | Range | Default | Unit | Description |
|---|---|---|---|---|---|
| **ROP** | `number_input` | 0 – 100 | 15.2 | m/hr | Rate of Penetration — speed at which the drill bit advances through the formation |
| **RPM** | `number_input` | 0 – 300 | 120.5 | RPM | Rotary Table Speed — drill string rotation frequency |
| **Torque** | `number_input` | 0 – 10,000 | 4,500 | ft-lbs | Surface Torque — rotational force measured at the top drive |
| **WOB** | `number_input` | 0 – 60 | 10.5 | klbs | Weight on Bit — axial load applied to the drill bit |
| **Current Bit Depth** | `number_input` | 1,000 – 5,000 | 2,780 | m | Measured depth of the drill bit, used as the corridor centre point |

ROP and Torque are displayed in the left column of a two-column layout; RPM and WOB in the right column. Bit Depth sits above the two-column block as a standalone full-width input.

<Note>
All five sensor inputs use `step` values that match field instrumentation resolution: ROP steps by 0.5 m/hr, RPM by 5, Torque by 100 ft-lbs, WOB by 0.5 klbs, and Bit Depth by 10 m.
</Note>

## Enable AI Risk Summary

Beneath the sensor inputs, a **Performance Controls** section contains a single checkbox:

```text
☐  Generate AI Risk Summary (Adds ~5s latency)
Default: unchecked
```

When checked, the dashboard sends the analysis payload to the Gemini LLM endpoint after the main UI renders, replacing the evidence string in the Operational Directive banner with a natural language explanation generated by Gemini. This mechanism uses **lazy loading**:

1. The user clicks **Run Drilling Risk Analysis** with the AI toggle enabled.
2. The form immediately submits and the main `analyze_drilling_risk` call executes with `enable_ai: False` — delivering instant ML metrics and offset well data.
3. The dashboard renders the full UI (KPI cards, map, tabs) with an interim evidence string of *"Gemini AI is analyzing offset wells..."*
4. The pending AI payload is stored in `st.session_state["pending_ai_payload"]`.
5. After the UI is fully painted, the lazy AI loader at the bottom of `app.py` fires `generate_ai_summary(payload)`, which POSTs to `{BACKEND_URL}/api/generate_ai_summary`.
6. The Gemini explanation overwrites the banner's evidence section in place via `render_directive()`.

<Tip>
Uncheck **Generate AI Risk Summary** for sub-second analysis turnaround. The full ML risk score, offset well map, and corridor metrics are available instantly without the LLM step. Enable AI only when you need a detailed natural-language explanation of the risk factors for shift handover reports or briefings.
</Tip>

## Running the Analysis

<Steps>

  <Step title="Configure parameters">
    Adjust the formation zone, search radius, depth corridor, and all five sensor inputs to match current rig conditions. Changes do not trigger any computation until the form is submitted.
  </Step>

  <Step title="Click Run Drilling Risk Analysis">
    Press the primary **Run Drilling Risk Analysis** button at the bottom of the sidebar form. This increments `st.session_state["run_count"]` (forcing map remounts) and opens a spinner: *"Analysing offset well incidents and spatial risk corridor..."*
  </Step>

  <Step title="API call to /api/analyze_risk">
    The dashboard POSTs a JSON payload to `{BACKEND_URL}/api/analyze_risk`:

    ```json
    {
      "location_area": "Duliajan Sector 4",
      "lat": 27.35,
      "lon": 95.32,
      "target_formation": "Kopili Shale",
      "depth": 2780.0,
      "rop": 15.2,
      "rpm": 120.5,
      "torque": 4500.0,
      "wob": 10.5,
      "search_radius_km": 5.0,
      "depth_window": 80.0,
      "enable_ai": false
    }
    ```

    The `enable_ai` field is always `false` in the primary call; Gemini is requested separately via the lazy loader if the checkbox was checked.
  </Step>

  <Step title="Session state updated">
    The API response is written to `st.session_state["dashboard_data"]`. The active radius and telemetry snapshot are stored in `st.session_state["active_radius_km"]` and `st.session_state["telemetry"]` respectively. All five tabs and the KPI cards re-render from this updated state.
  </Step>

</Steps>

If the backend is unreachable, `api_client.py` catches the exception and returns a structured fallback response with `risk_level: "UNKNOWN"` so the dashboard continues to render without crashing.

## Safe Operating Envelopes

The `TELEMETRY_THRESHOLDS` dictionary in `config.py` defines the boundaries of the safe operating envelope for all four drilling parameters. These thresholds govern both the gauge card status badges in Tab 4 and the overall MSE interpretation.

| Parameter | Min (safe lower bound) | Normal Max (safe upper bound) | High Risk Threshold | Unit |
|---|---|---|---|---|
| **ROP** | 5.0 | 25.0 | 35.0 | m/hr |
| **RPM** | 60.0 | 150.0 | 180.0 | RPM |
| **Torque** | 1,000 | 5,000 | 6,500 | ft-lbs |
| **WOB** | 4.0 | 20.0 | 28.0 | klbs |

Each parameter is evaluated independently against these ranges on every dashboard render:

- **Below `min`**: yellow warning status (e.g. *"Low ROP — Pack-off Risk"*, *"Low RPM — Sticking Risk"*).
- **Between `min` and `normal_max`**: green safe status.
- **Between `normal_max` and `high_risk`**: yellow elevated warning.
- **Above `high_risk`**: red critical status (e.g. *"Critical Over-Torque"*, *"String Buckling Risk"*).

The envelope thresholds are also used when computing the **Teale's MSE** indicator. An MSE above 90 kpsi signals elevated mechanical drag; above 160 kpsi indicates critical pack-off or bit balling conditions.

```python
# From config.py
TELEMETRY_THRESHOLDS = {
    "rop":    {"min": 5.0,    "normal_max": 25.0,   "high_risk": 35.0,   "unit": "m/hr"},
    "rpm":    {"min": 60.0,   "normal_max": 150.0,  "high_risk": 180.0,  "unit": "RPM"},
    "torque": {"min": 1000.0, "normal_max": 5000.0, "high_risk": 6500.0, "unit": "ft-lbs"},
    "wob":    {"min": 4.0,    "normal_max": 20.0,   "high_risk": 28.0,   "unit": "klbs"},
}
```

<Warning>
Operating outside the safe envelope does not directly modify the ML risk score produced by the backend — that score is based on historical incident density in the offset corridor. Envelope violations are a separate real-time safety layer displayed visually in Tab 4. However, formations with high historical incident density at similar ROP/Torque exceedances should be treated as compounded risk.
</Warning>
